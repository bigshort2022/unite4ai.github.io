# Registered Baselines and Run Cost Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans. Steps use checkbox syntax for tracking.

**Goal:** Make predeclared setups and per-success costs visible before collecting or comparing new results.

**Architecture:** Markdown baseline manifests join to immutable results by an exact setup key; there is no editable `baseline: true` flag. The runner is local by default. Its paid path is opt-in, reads owner approval from a local file and credentials from the contributor's environment, and emits only reproducible public metadata. All deployment and CI paths are static and offline with respect to models and pricing.

**Tech stack:** Bun, TypeScript, Zod, Astro, Python 3 for the existing BFCL checker.

**Spec:** [`Registered baselines` and `Cost per success`](../specs/2026-11-22-agent-evidence-design.md). Built on Plan 3 / #40. Do not start, restart, or reconfigure servers. Standing owner approval covers spare local capacity on M5 and the mini's 8082 only (never 8080); not API spending.

## Task 2: Offline accounting and explicitly approved API runs

**Files:** `packages/schema/src/index.ts`, `apps/web/src/content.config.ts`, `packages/core/src/eval-cost.ts`, `packages/core/package.json`, `apps/cli/src/eval/{api,args,client,run,speed}.ts`, `apps/cli/test/{api,run-eval}.test.mjs`, `CONTRIBUTING.md`.

- [ ] Add tests for refusal before HTTP when approval/key/model/origin/terms/budget is absent, mismatched, or invalid; authenticated streaming without logged credentials or redirects; hash-pinned lookup from a fixture catalog and missing usage; correct/incorrect attempts, zero successes, and invoice scope. All use fixtures or a test harness; no calls to providers in tests.
- [ ] Accept `--api-approval <local JSON>` only with `--runtime api`. The file binds `benchmark`, `benchmark_version`, served model, submitter, exact HTTPS `base_url`, `provider` (models.dev ID), optional external `model_card`, `terms_url`, `terms_checked_on`, `expected_usd`, `approved_usd` (`0 <= expected <= approved`, approval positive). The local credential is `U4AI_EVAL_API_KEY`. No redirects or credentials in URL components/query/fragment, no response bodies in authenticated errors. Do not auto-select a provider, provision an account, retry paid requests, or treat the stated budget as an enforced provider cap. Contributors must set a provider-side cap before using the key. Keep API-only evidence separate from the open registry. Require repeat mode and do not emit measured speed companion results for API runs. Any hardware on API results is the client; provider device and weight format are unknown.
- [ ] Expose public `api` metadata (`provider`, optional `model_card`, `terms_url`, `terms_checked_on`, `expected_usd`, `approved_usd`) and `cost` only when attributable. Optional `--price-snapshot`, `--price-date` and `--price-sha256` must appear together. Read bytes locally, match SHA-256, then use `[provider].models[servedModel].cost.{input,output}` in USD per million. Cost record: `kind: 'models-dev'`, `snapshot_date`, `snapshot_sha256`, `input_usd_per_million`, `output_usd_per_million`, `total_usd`, optional `usd_per_success`. Formula: `(prompt_tokens_total × input_usd_per_million + completion_tokens_total × output_usd_per_million) / 1e6`. Round only the display; use the same function in runner and gate. If either usage total is unknown do not emit an estimate. An estimate is a list-price estimate for completed answers, not the bill; discounts, surcharges and billed failures outside the transcript can differ. Alternative `invoice` with `invoice_sha256`, `total_usd` and optional `usd_per_success` is contributor-supplied post-run, explicitly the attributable USD amount (including billed failed requests). Never commit an invoice, price-catalog download, credentials, or approval file. Gate checks shapes, terms timing, and arithmetic; invoice provenance is a contributor assertion. Both kinds divide by `sum(repeat.run_correct)` and omit the ratio for zero successes. For local runs show time and available tokens per successful attempt, no USD; report energy only if a measured total is available (never estimate it from the machine name).
- [ ] Keep the existing local path and legacy results valid. Local runs never read a paid key; record served ID with the result, already recorded in transcripts. Strip credentials, queries and fragments from published URLs. Approval and price snapshot local paths must not be in published commands. Privileged fields do not go into transcripts or server errors. Run `bun test apps/cli/test/api.test.mjs apps/cli/test/run-eval.test.mjs`.

## Task 3: Compute tool-only floors and gate BFCL publication

**Files:** `scripts/benchmarks/baseline-floors.ts`, `scripts/benchmarks/baseline-floors.test.mjs`, `scripts/benchmarks/bfcl_crosscheck.py`, `apps/web/src/content/benchmarks/{tool-selection-v1,bfcl-multiple-50}.md`, `packages/core/src/validate-evals.ts`.

- [ ] Compute the two floors directly from the pinned item sets, offline from the committed synthetic items and the hash-checked BFCL fixtures. For tool selection, `null` is explicitly offered on every item; `p = 1/(tools.length + 1)` even for an abstention. BFCL multiple has no abstention item, `p = 1/functions.length`. Use gold arguments when the tool guess is correct: these are tool-only references, not full-call performance. Report exact counts/fractions or expected percentages `mean(p)` and `mean(p ** 5)` for independent random choice and the fraction of gold names at index zero for both first-tool rates. No floor for the canary, which offers no tool-choice menu. Test that documented numbers match the checked inputs; no sampling or model use.
- [ ] Extend `bfcl_crosscheck.py transcript` to reject incomplete, duplicate/out-of-order or differently pinned transcripts and replay raw replies with the pinned Bun judge. Its compact JSON output has the transcript hash and an ordered boolean for every attempt; derive counts and disagreement coordinates from the array, don't store them twice. The gate requires a report before publishing any BFCL v1 result. The hash must match a registered BFCL v1 result, and each disagreement needs an explanation keyed by its zero-based answer position, rendered on the benchmark page. No report is required while no BFCL results exist. Test the gate using fixtures only.
- [ ] Merge code and manifests **before** running the first registered baselines. Check the M5 is on AC and its exact loaded model has no active requests; for mini use only 8082 and confirm idle independently of the `/v1/models` list. Run one registered BFCL baseline at a time when idle; if a server is missing or capacity is ambiguous, do not run or change it. For the first BFCL result, run `python3 scripts/benchmarks/bfcl_crosscheck.py transcript <transcript>`; review agreement, publish the compact report and result in a separate PR, keep the raw transcript local. The 4B entry waits until it is the model already loaded. No frontier run until the selected model, endpoint, publishable terms and spend are agreed by the account owner (across all three suites: 1,000 requests for one setup, with suite-specific prompt lengths).
