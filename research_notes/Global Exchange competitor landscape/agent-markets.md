# Agent markets: five-project competitor landscape

## 1. Comparison and scope

### Takeaway

These five projects are not interchangeable compute exchanges. Virtuals ACP and Olas Mech Marketplace sell agent-delivered tasks; SingularityNET sells callable AI services; Fetch.ai/ASI Agentverse primarily supplies discovery and interaction; Bittensor coordinates token-incentivized subnet production. The classifications below are analytical judgments grounded in the cited official product documentation, not claims of equivalent hardware rental functionality.

**Research cutoff and retrieval date:** 2026-11-18 for every URL cited below. Retrieval means reading official web documentation or a public page, not signing in, executing agents, paying, or testing settlement. No market-size, transaction-volume, audit, or production-safety claims are made. Fetch.ai/ASI is counted once, including Agentverse, ASI:One discovery, and its associated payment messaging.

## 2. Per-project evidence notes

### Virtuals Protocol ACP

**Cited findings**

- Current concepts separate agent identity from capabilities. Offerings contain name, description, price, SLA, input requirements and deliverable; resources are unpriced read-only endpoints. Service-only jobs are explicitly distinguished from jobs managing the client's principal funds. This matters because buying an analysis is a different trust exposure from granting a trading agent capital. [Core concepts](https://os.virtuals.io/acp/concepts)
- The current state machine is `open → budget_set → funded → submitted → completed`, with rejection/expiration branches. Approval releases escrow; rejection returns it. These are documented mechanics, not measured execution guarantees. [Core concepts](https://os.virtuals.io/acp/concepts)
- Butler's human flow connects a wallet, accepts a Privy-managed Butler wallet, deposits Base-mainnet USDC and submits a natural-language task. The guide says Butler chooses a research agent, negotiates, escrows payment and returns an on-chain receipt. It calls ACP live but early beta. [Butler quick-start](https://whitepaper.virtuals.io/info-hub/user-hub/butler-quick-start-guide)
- The older technical deep dive describes request/negotiation/transaction/evaluation phases and a simulated lemonade-stand experiment, while its closing text still says a beta release is upcoming. Treat that page as design/demo evidence, not current launch status. [Technical deep dive](https://whitepaper.virtuals.io/about-virtuals/commerce-layer/technical-deep-dive)
- Evaluation behavior is version-sensitive: the older onboarding page says omitting `onEvaluate` invokes a default approval handler that releases escrow, whereas EconomyOS concepts say the client assumes the evaluator role when none is specified. Neither warrants the blanket statement “all ACP output is independently verified.” [Optional evaluation](https://whitepaper.virtuals.io/acp/acp-dev-onboarding-guide/tips-and-troubleshooting/optional-evaluation-in-acp), [Current concepts](https://os.virtuals.io/acp/concepts)

**Inferences**

- ACP is a strong comparator for a machine-readable task request/offer/receipt lifecycle, but its contracts, wallets and execution services cannot be inferred to exist in a static GitHub Pages exchange. The supplied design can publish compatible-looking metadata without claiming to execute ACP transactions. [Underlying lifecycle](https://os.virtuals.io/acp/concepts)

**Gaps / source conflicts**

- The Butler guide's introductory text mentions VIRTUAL while its actual deposit instructions require USDC; its displayed update date is 2025-11-04 although an embedded screenshot filename includes 2025-11-19. Use the current concepts plus explicit deposit instructions for documented USDC support, and do not rely on the page's timestamp as a precise revision history. Wallet recovery/export policies, current upgrade powers and practical refund timing were not established. [Butler guide](https://whitepaper.virtuals.io/info-hub/user-hub/butler-quick-start-guide)

### Olas / Autonolas Mech Marketplace

**Cited findings**

- A Mech is a registered AI agent offering tools. Requests can store prompt/tool/nonce data on IPFS, write its hash to the marketplace, trigger off-chain execution, and publish a response hash on-chain for the requester to retrieve. The client also supports directly sending off-chain requests with subsequent on-chain delivery. [Server workflow](https://stack.olas.network/mech-server/), [Client workflow](https://stack.olas.network/mech-client/)
- The server guide advertises deadline-based takeover by another Mech and Karma reputation. Its wording “Guaranteed Task Completion” is stronger than the actual stated mechanism: takeover permits another available Mech to respond; it does not demonstrate that a capable replacement will always exist. This distinction is an inference from the mechanism, not a separately tested failure result. [Marketplace description](https://stack.olas.network/mech-server/)
- Client mode uses an externally owned account; default agent mode registers activity through a Safe multisig. The client discovers the payment type from the Mech contract and supports prepaid or per-request flows. It says `maxDeliveryRate` is a maximum charge and actual settlement can be lower. [Client docs](https://stack.olas.network/mech-client/)
- The client explicitly warns that reciprocal operator-domain metadata does not prove the same party controls the domain and Mech; names are claimed, benchmarks are operator-supplied links, and Olas does not review Mechs. Undelivered off-chain requests never enter the on-chain counts, so those counts cannot establish an unbiased completion rate. [“Who runs a Mech”](https://stack.olas.network/mech-client/)
- The official marketplace returned a server-rendered registry snapshot dated 2026-11-18 11:07 UTC, with named registered services and service IDs. This is observed listing evidence only; registration is not proof of live task availability, customer revenue or validated output. [Observed registry page](https://marketplace.olas.network/ethereum/ai-agents)

**Inferences**

- Olas supplies an especially useful pattern for Global Exchange: separate operator claims, mechanically checked identifiers, delivery observations and external benchmarks rather than compressing them into a “verified provider” badge. [Client trust disclosures](https://stack.olas.network/mech-client/)

**Gaps / source conflicts**

- The current client support table lists Nevermined subscriptions on Gnosis and Base but not Polygon/Optimism; the server table marks Nevermined available on all four. Client docs additionally mention Robinhood/USDG, absent from the server overview. Do not publish one universal payment-support matrix without checking the precise client/server version, chain and Mech contract. No deposit, request or refund was attempted. [Client table](https://stack.olas.network/mech-client/), [Server table](https://stack.olas.network/mech-server/)

### SingularityNET

**Cited findings**

- The marketplace lists services, supports web invocation and ratings, and indexes blockchain organization/service events into a database. The marketplace application is deliberately separate from the decentralized registry. A service can be published to the network without being listed in the marketplace UI. [Marketplace architecture and requirements](https://dev.singularitynet.io/docs/products/AIMarketplace/)
- Service scope includes inference, model training and specialized AI algorithms. Providers can deploy autonomous agents interoperating with other services, but the marketplace's basic transaction unit is a service invocation, not a reserved GPU or VM. [Marketplace scope](https://dev.singularitynet.io/docs/products/AIMarketplace/)
- Current documentation calls the payment token ASI (FET). MPE provides deposits/withdrawals plus atomic unidirectional payment channels. Consumers fund expiring channels and sign authorizations; providers verify signatures/amounts and claim on-chain. Remaining funds can be reclaimed after channel expiry. The daemon maintains off-chain channel state to reduce blockchain interactions. [MPE documentation](https://dev.singularitynet.io/docs/products/DecentralizedAIPlatform/CoreConcepts/SmartContracts/mpe/)
- The public marketplace URL returned its title and product description but no inspectable service catalog in this text retrieval. That is public-site availability evidence, not proof of any particular working service. [Marketplace](https://marketplace.singularitynet.io/)

**Inferences**

- This is a relevant direct competitor when “compute for tasks” means buying an AI result via an API. MPE protects payment-channel accounting; the documented mechanism does not establish semantic correctness of model responses or automatic commercial dispute resolution. [Service scope](https://dev.singularitynet.io/docs/products/AIMarketplace/), [MPE](https://dev.singularitynet.io/docs/products/DecentralizedAIPlatform/CoreConcepts/SmartContracts/mpe/)

**Gaps / source conflicts**

- MPE's narrative examples inconsistently swap buyer/seller names and use “AFET”; the clearer structural description and contract API are preferable to those prose examples. Exact current token contract/chain migration status, channel deployment configuration, current listing requirements and service liveness were not independently checked. The marketplace requirements section also contains unfinished-paperwork wording, so it should not be treated as a verified current onboarding SLA. [MPE](https://dev.singularitynet.io/docs/products/DecentralizedAIPlatform/CoreConcepts/SmartContracts/mpe/), [Listing requirements](https://dev.singularitynet.io/docs/products/AIMarketplace/)

### Fetch.ai / ASI — counted once

**Cited findings**

- Agentverse calls its marketplace an “Almanac Explorer”: users search agents by address/protocol and filter deployment type, state and trust. The docs distinguish hosted, local, mailbox, custom and proxy agents. Compatible agents expose a “Chat with Agent” experience through ASI:One. [Marketplace documentation](https://docs.agentverse.ai/documentation/getting-started/agentverse-marketplace)
- Agent metadata and behavior influence discovery rankings; registration and an active tag indicate aspects of registration/connectivity, not a standardized priced service contract. The Testing feature evaluates prompt responses and explicitly distinguishes useful answers from merely delivered replies. [Marketplace](https://docs.agentverse.ai/documentation/getting-started/agentverse-marketplace), [Testing](https://docs.agentverse.ai/documentation/agent-discovery/testing)
- The uAgents Agent Payment Protocol version shown is `0.1.0`, with `RequestPayment`, `CommitPayment`, `RejectPayment`, `CompletePayment` and `CancelPayment`. Funds encode amount, currency and payment method; examples mention USDC/Skyfire and a default `fet_direct` method. These are message/rail identifiers, not proof every listed agent accepts those currencies. [Payment protocol](https://uagents.fetch.ai/docs/guides/agent-payment-protocol)
- The example buyer sends `transaction_id="demo-txn-001"` and the seller replies with a completion message. No transfer or settlement verification occurs in that example. Treating it as a working paid checkout would be unsupported. [Payment example](https://uagents.fetch.ai/docs/guides/agent-payment-protocol)
- Agentverse's overview describes monetization options but also labels monetization tools “Coming soon”; the marketplace document promises “monetization potential.” Those statements do not establish universally operational marketplace billing. Direct retrieval of the application URL returned HTTP 403 bot protection. [Overview](https://docs.agentverse.ai/documentation/getting-started/overview), [Marketplace docs](https://docs.agentverse.ai/documentation/getting-started/agentverse-marketplace), [Attempted app](https://agentverse.ai/)

**Inferences**

- Fetch.ai/ASI is primarily the discovery and orchestration comparator for this research slice. Payment messaging can complement discovery, but an actual rail, spending authorization, transaction validation and service-delivery policy still have to be implemented. Agentverse, ASI:One and the uAgents protocol must not become three duplicate competitors in the twenty-project landscape. [Discovery](https://docs.agentverse.ai/documentation/getting-started/agentverse-marketplace), [Payment messages](https://uagents.fetch.ai/docs/guides/agent-payment-protocol)

**Gaps / source conflicts**

- Payment-model bullet descriptions reverse buyer/seller responsibilities relative to the page's explicit role map and “Basic Payment Flow”; the role map and runnable handlers agree that seller requests, buyer commits/rejects, and seller completes/cancels. Exact implemented behavior must be checked against a pinned library version before integration. Current settlement, custody and dispute policies cannot be inferred from this message specification. [Protocol roles and examples](https://uagents.fetch.ai/docs/guides/agent-payment-protocol)

### Bittensor

**Cited findings**

- The chain coordinates participation and economic rewards while actual work occurs off-chain within independent subnets. Subnet owners set mechanisms, miners produce outputs and validators submit scoring weights. This is a competitive incentive market, not a buyer-issued purchase order lifecycle. [Network](https://www.bittensor.com/docs/concepts/network)
- Current docs distinguish TAO from each subnet's alpha token. Staking into a subnet swaps TAO for alpha; unstaking swaps back, with price/fees/slippage considerations. Emissions occur through chain allocation and per-epoch distribution informed by Yuma Consensus, rather than directly representing customer payments for individual tasks. [Network](https://www.bittensor.com/docs/concepts/network), [Emissions](https://www.bittensor.com/docs/concepts/emissions)
- Validator influence is stake-weighted and subnet-owner-defined scoring runs off-chain. A subnet's engineering mechanism therefore determines what is rewarded; token payout itself is not cryptographic proof that an end customer's task was correctly completed. The latter is an inference from the documented division between off-chain mechanisms and on-chain weights. [Subnet guide](https://www.bittensor.com/docs/guides/subnets), [Yuma mechanics](https://www.bittensor.com/docs/concepts/emissions)
- Documentation publishes Finney mainnet and testnet endpoints, SDK/CLI interaction patterns, and source-linked chain rules. These are substantially more concrete than a conceptual proposal, but no endpoint query, miner deployment, workload request or token transaction was executed in this research. [Network endpoints](https://www.bittensor.com/docs/concepts/network), [Subnet operations](https://www.bittensor.com/docs/guides/subnets)

**Inferences**

- Global Exchange could list a specific subnet-backed inference provider as a service supplier with its own endpoint, operator, price and terms. It should not present “Bittensor” as one universally purchasable compute SKU, imply staking buys task capacity, or treat emissions as task revenue. [Subnet independence](https://www.bittensor.com/docs/concepts/network), [Reward mechanics](https://www.bittensor.com/docs/concepts/emissions)

**Gaps**

- This scoped study did not select or test a particular subnet API, buyer price, gateway custody model or service SLA. The legacy understanding-subnets URL redirected to the current documentation root, so current network/emissions guides underpin the findings rather than assuming old token mechanics remain valid. [Legacy URL](https://docs.bittensor.com/subnets/understanding-subnets), [Current network](https://www.bittensor.com/docs/concepts/network)

## 3. Implications for the approved static exchange

### Inferences

- **Keep directory truth separate from execution truth.** Given the supplied GitHub Pages/Git-records/no-platform-running-cost constraint, the immediately compatible competitive layer is discoverable provider/offer records, documented human and agent handoffs, and externally verifiable evidence links. This is a recommendation, not a claim that a wallet, payment processor, escrow or job runner already exists. Agentverse's metadata model and Olas's claim-versus-observation disclosures are useful precedents. [Agentverse marketplace](https://docs.agentverse.ai/documentation/getting-started/agentverse-marketplace), [Olas client](https://stack.olas.network/mech-client/)
- **Represent the transaction unit explicitly.** Suggested analytical categories are task deliverable (ACP/Olas), callable AI service (SingularityNET), agent discovery/integration (Fetch.ai/ASI), and subnet-produced service/incentive network (Bittensor). Do not combine hourly compute, per-request API fees, agent work budgets and staking into a single “compute price.” [ACP offerings](https://os.virtuals.io/acp/concepts), [Mech payments](https://stack.olas.network/mech-client/), [SNET services](https://dev.singularitynet.io/docs/products/AIMarketplace/), [Agentverse](https://docs.agentverse.ai/documentation/getting-started/agentverse-marketplace), [Bittensor](https://www.bittensor.com/docs/concepts/network)
- **Avoid unsupported verification badges.** Distinguish publisher identity claims, domain linkage, signed records, observed availability, paid delivery receipts, output-quality evaluation and dispute outcomes. The strongest cautionary examples are Olas's admitted off-chain reporting blind spot, ACP optional auto-approval and Fetch's payment messages without actual settlement. [Olas limitations](https://stack.olas.network/mech-client/), [ACP evaluation](https://whitepaper.virtuals.io/acp/acp-dev-onboarding-guide/tips-and-troubleshooting/optional-evaluation-in-acp), [Fetch payment example](https://uagents.fetch.ai/docs/guides/agent-payment-protocol)

### Remaining gaps

No evidence collected establishes uniform operational availability, comparative unit economics, independent audits, production safety, quality-adjusted performance, legal recourse or successful purchases across these five projects. Documentation, observed public listings, a marketing launch claim, a demo and a verified end-to-end transaction are different evidence levels; only the first three were available here, with the limits specified per project.
