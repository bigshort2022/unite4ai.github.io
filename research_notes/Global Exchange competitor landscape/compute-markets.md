# Compute markets: five existing projects

## 1. What do the five projects actually sell?

### Takeaway
These are compute-market comparators, not interchangeable payment protocols: Akash, io.net and Vast.ai expose infrastructure rental; Golem exposes negotiated execution/rental through a decentralized protocol; Render primarily sells completed rendering work. Inference is either a separately managed API or a workload deployed on rented infrastructure, not automatically the same product as a GPU rental. Sources and qualifications appear in each row and the evidence notes below.

**Research retrieved:** 2026-11-18. All sources below are official project documentation or official product pages retrieved on that date. “Documented” means a first-party product/interface description, not an independently executed rental, payment, benchmark or provider payout. No external accounts, jobs or transactions were created. Prices are documented units/rates, not live offers or market averages. Exactly five projects are covered; product/subnet names are not additional project rows.

### Inferences
- **[INFERENCE]** All five compete for compute demand, but Render is a specialist comparator rather than a substitute for every general compute task. Their crypto associations do not turn them into generic payment protocols.

### Gaps
- No independent operational proof was collected: no successful paid deployment, delivered task, withdrawal or provider settlement was observed. No market-share, revenue, utilization or available-capacity estimate is asserted.

## 2. What evidence and caveats matter project by project?

### Akash Network

**Cited findings**
- Deployment is a container-resource request described by SDL; providers bid, the tenant accepts a lease, and the provider starts the container. Current core docs describe ACT as a USD-pegged compute credit, paid from escrow per block, approximately six seconds. They also mention AKT fallback when a circuit breaker applies. Do not reduce current billing to “always AKT” or “always USDC.” [Core concepts](https://akash.network/docs/getting-started/core-concepts/)
- Managed Console accepts card-funded USD credits (plus trials/coupons), converts them behind the scenes and automatically maintains deployment escrow. The funding page distinguishes available balance from escrow and returns unused escrow to available credits when a deployment closes. This is an account-credit return, not documented cash withdrawal. CLI/Console Air users instead fund their own deployment escrow. [How funding works](https://akash.network/docs/getting-started/how-funding-works/)
- Human operators can use Console; agents can use Console API with managed-wallet credentials or CLI/SDK with a funded self-custody wallet. The official agent skill covers deployment, bid acceptance, manifests, logs and managed inference through AkashML. This is genuine agent-facing documentation, not evidence that an agent autonomously funded and completed a purchase during this research. [AI agents](https://akash.network/docs/getting-started/ai-agents/)
- For an official audited-provider badge, current instructions require on-chain attributes, conventional DNS/TLS, reachable provider ports, Discord contact, benchmark deployment and reviewer sign-off through a GitHub issue. Standalone audit thresholds include 500 Mbps up/down, 64 available CPU cores and 128 GiB RAM; smaller GPU operators are directed to Homenode. These are **audit eligibility thresholds**, not a claim that every possible network participant has identical entry requirements. [Provider audit](https://akash.network/docs/providers/operations/provider-audit/)

**Inferences and limitations**
- **[INFERENCE]** Attribute review and hardware benchmarks help select a provider; they do not establish cryptographic correctness of arbitrary task outputs, privacy guarantees or a universal service-level guarantee. “Audited provider” here must not be conflated with an independent security audit of all contracts/software.
- **Gap:** We did not verify ACT peg/redemption economics, a running lease, a provider payout, current GPU offers or managed-inference token rates. Documentation examples are not live price quotes.

### io.net

**Cited findings**
- The current Cloud overview distinguishes self-service VM/container deployment from managed Bare Metal, Kubernetes, Ray and Confidential Compute clusters, for which users email sales. Thus “all distributed cluster configurations are immediately API-self-service” would overstate the retrieved evidence. [Cloud overview](https://io.net/docs/guides/clouds/start-using-io-cloud)
- IO Intelligence has account/API-key onboarding and OpenAI-compatible chat-completion endpoints for hosted open-source models, separately from infrastructure rental. The API guide mentions model-specific free daily limits; it does not establish one universal paid per-token rate. [IO Intelligence APIs](https://io.net/docs/guides/intelligence/io-intelligence-apis)
- IO Credits are USD-equivalent account credits; the credit page documents a USD 10 minimum purchase, USDC via Spherepay and card via Stripe, `payment_method: "credits"`, and account transaction history. Purchased-credit withdrawal requires manual finance review, normally three to seven business days; purchased credits expire after twelve months and expired value is not recoverable. [IO Credits](https://io.net/docs/guides/payment/io-credits)
- Cloud PAYG charges the first hour upfront without refund for voluntary early termination, then charges every few minutes ahead of runtime. A supplier can change the running booking's price for subsequent charges. Insufficient balance terminates bookings and removes them; provider-side failure can trigger refund of prepaid time. [PAYG](https://io.net/docs/guides/payment/pay-as-you-go)
- Worker onboarding requires supported hardware, proof-of-work verification, cluster-readiness checks and staking for job/reward eligibility; it documents an initial twelve-hour waiting/readiness process. Workers must use the official binaries/images and dedicated capacity while contributing. [Device onboarding](https://io.net/docs/guides/workers/device-onboarding)
- Rewards docs state all worker earnings are paid in IO Coin and describe wallet-linked claims plus separately hourly block rewards. Reward emissions are supply incentives and must not be equated with revenue from paid customer jobs. [Rewards/wallets](https://io.net/docs/guides/workers/rewards-wallets)

**Conflicts, inferences and limitations**
- **Source inconsistency:** Credit documentation lists USDC/card purchase methods, while Cloud/PAYG also mention IO Coin top-ups. The worker-wallet guide says IO Coin earnings but retains a “click USDC” withdrawal instruction. Report confirmed account-credit billing and documented IO earnings; do not assert every funding/withdrawal rail works today without checking the actual product. [Credits](https://io.net/docs/guides/payment/io-credits), [PAYG](https://io.net/docs/guides/payment/pay-as-you-go), [rewards](https://io.net/docs/guides/workers/rewards-wallets)
- **Source inconsistency:** General credits prose says unused funds from early termination are returned as credits, whereas the specific PAYG page explicitly denies refund of unused prepaid time when users stop a booking. Use the **PAYG-specific rule for PAYG**, not the general sentence as a universal refund promise. [Credits](https://io.net/docs/guides/payment/io-credits), [PAYG](https://io.net/docs/guides/payment/pay-as-you-go)
- **[INFERENCE]** Distributed hardware supply does not eliminate trust in the hosted account ledger, orchestration, supplier verification or withdrawal reviewers. A proof-of-work hardware check is not proof that a particular inference answer is correct.
- **Gap:** No inference tariff, worker payout, token conversion spread or live cluster success was independently verified.

### Golem Network

**Cited findings**
- Golem's payment protocol uses GLM on Ethereum or supported lower-cost networks; requestors also fund transaction fees. Usage pricing combines negotiated coefficients for activity start, elapsed environment time and processor time. The provider FAQ explicitly defines CPU/hour as thread utilization: four threads at 0.1 GLM/CPU-hour cost 0.4 GLM for one hour. These are examples of units, not a network-wide tariff. [Payments](https://docs.golem.network/docs/golem/payments), [Provider FAQ](https://docs.golem.network/docs/providers/provider-faq)
- Providers meter resource usage and issue invoices; requestors accept/pay them. Keep-alive debit notes establish continued participation; negotiated mid-agreement payable debit notes reduce prolonged unpaid exposure. The docs explicitly acknowledge requestor dishonesty/nonpayment risk, so this must not be described as guaranteed escrow settlement. [Payments](https://docs.golem.network/docs/golem/payments)
- The GPU inference tutorial installs Yagna, funds GLM and POL on Polygon mainnet, uses `@golem-sdk/golem-js`, selects `vm-nvidia` with `!exp:gpu`, deploys Ollama and creates a local TCP proxy. Its sample cap of 2 GLM/environment-hour is an example configuration, not the market price. The page says GPU providers are available on mainnet but not its testnet; CPU testnet examples use valueless test GLM. [GPU tutorial](https://docs.golem.network/docs/creators/javascript/tutorials/AI-on-golem-network)
- The general provider FAQ requires x86-64 Linux and virtualization support, explicitly excluding ARM/macOS provider operation. Providers configure their prices; price changes affect new agreements, not ongoing ones. Selection can consider hardware, price, reputation and provider identity. Task arrival depends on demand/hardware fit/pricing and is not guaranteed. [Provider FAQ](https://docs.golem.network/docs/providers/provider-faq)

**Inferences and limitations**
- **[INFERENCE]** The requestor service is an agent-compatible executor but does not mean a human obtains turnkey GPU inference merely by opening a webpage. Wallet funding, gas, image preparation, daemon lifecycle and result checking remain integration responsibilities.
- **Gap:** General provider setup requirements should not be silently treated as a complete GPU-provider admission checklist. No GPU-provider onboarding run, task-level correctness mechanism, current capacity or payment transaction was verified. The experimental-looking GPU capability marker is visible in the sample; it is not enough by itself to assign a formal maturity label.

### Vast.ai

**Cited findings**
- Hosts set prices. Buyers can search web offers or use `vastai search offers`/the API. On-demand, reserved, interruptible and serverless modes share marketplace capacity; interruptible jobs can be paused when outbid. Serverless is autoscaled worker infrastructure suitable for inference, not necessarily a fixed price per generated token. [Pricing overview](https://docs.vast.ai/guides/pricing)
- Billing separates GPU USD/hour, storage USD/GB/hour and bandwidth USD/TB. Active compute is metered per second and bandwidth per byte. Stopping an instance does not stop storage charges; offline instances are documented as exempt from active rental and storage charges. Serverless pricing overview says underlying worker costs apply without an added serverless surcharge. [Billing](https://docs.vast.ai/guides/reference/billing), [Pricing overview](https://docs.vast.ai/guides/pricing)
- Buyers prepay credits through card/crypto processors. Credits exhausted means stopped instances and eventual deletion risk; saved cards may be charged to cover negative balances. Spent credits are nonrefundable; the FAQ says crypto-purchased credits are not refunded. The general unspent-credit paragraph is broader, so do not promise a crypto refund. [Billing](https://docs.vast.ai/guides/reference/billing)
- Verification uses proprietary operational/performance algorithms and can be removed. The page sets dedicated Ubuntu-host, GPU/CUDA, storage, bandwidth/public-IP/ports and reliability requirements and says meeting minimums does not guarantee verification. It also prioritizes high-demand GPUs, so a verification label reflects platform admission/operational criteria rather than only intrinsic hardware performance. [Verification stages](https://docs.vast.ai/host/verification-stages)
- Hosts choose Wise, PayPal or Stripe and must satisfy regional B2B-payment and identity/tax requirements. USD 20 is the minimum invoice threshold; invoices are generated Fridays and generally paid in the following Friday cycle, with further processor delays possible. A platform “Paid” state means submission to the processor, **not confirmed arrival in the host's bank/account**. [Host payouts](https://docs.vast.ai/host/payment)

**Inferences and limitations**
- **[INFERENCE]** Distributed hosts do not make the marketplace's payments decentralized. Verified status is not an independent security audit or proof of arbitrary computation. Budgeting must include storage, bandwidth, interruption risk and host/platform trust, not only advertised GPU-hour cost.
- **Gap:** No authenticated offer, machine reliability measurement, serverless endpoint or payout was tested. Documentation's broad “guaranteed uptime” marketing is not treated as a reviewed contractual SLA.

### Render Network

**Cited findings**
- The documented customer unit of work is a scene/job/frame workflow: prepare supported scene assets, upload, create a test job, inspect/approve frames and download outputs. Automatic approval bypasses manual review. That differs from choosing a machine and receiving unrestricted shell access. [Quickstart](https://know.rendernetwork.com/docs/get-started/quickstart.md)
- The Manager app's local API supports programmatic job submission, status/output management, presets and frame retrieval. API access requires whitelisting and a personal access token; therefore “has an API” does not mean unrestricted, permissionless remote access from any new agent. [Render API](https://know.rendernetwork.com/the-render-network-api)
- The current official price page lists **€0.60/400 OBh Economy, €1.20/400 OBh Standard, €2.40/400 OBh Performance**; Enterprise **€4.00/400 OBh is explicitly “To Be Released.”** It says actual GPU time is billed down to the minute. Bandwidth is **0.09 credits per GB of scene assets transferred to nodes**, only for successfully rendered frames; distributing one asset set to multiple nodes multiplies transferred data. [Current pricing](https://rendernetwork.com/pricing)
- Current credit instructions state one Render Credit costs **€1**, minimum purchase one credit, payment through Stripe or PayPal, and credits are rendering-only/nonwithdrawable. [Buy Render Credits](https://know.rendernetwork.com/docs/web-app/render-credits.md)
- BME documentation describes fiat-equivalent job pricing, conversion to/burning of RENDER on completed work, and separate network-emission allocation at epoch ends, typically weekly. RENDER is described as transacted/emitted on Solana. This is not a guarantee that a customer's exact token amount immediately transfers to its individual rendering operator. [BME](https://know.rendernetwork.com/basics/burn-mint-equilibrium)
- Rendering node operators submit an interest form and await onboarding; recommended hardware includes CUDA NVIDIA GPU, 6 GB minimum recommended VRAM (8+ preferred), 32+ GB RAM and 100 GB free disk. [Rendering operator onboarding](https://know.rendernetwork.com/general-render-network/what-role-am-i/how-to-get-started-1)
- The separate AI-workload subnet, now called **Dispersed**, has a benchmark/speed-test waitlist. Its page explicitly says neither entry into a cohort nor work allocation is guaranteed and warns against buying new hardware to join. It contains an unresolved storage inconsistency: introductory requirements say 2 TB+ SSD, while a later answer says 1 TB NVMe per node and links its proposal. [AI compute waitlist](https://know.rendernetwork.com/general-render-network/what-role-am-i/how-to-get-started-1/render-compute-network-gpu-compute-node-waitlist-faq)

**Conflicts, inferences and limitations**
- **Source conflict:** Older knowledge-base pricing describes three tiers (Trusted unreleased, Priority, Economy), token/credit-to-OBh examples and no current Performance tier. The current official price page explicitly describes Standard as formerly Priority and Performance as new. For current comparison, use the explicit euro/400-OBh price page and retain the older article only as evidence of documentation drift; do not convert historical RNDR examples into a current tariff. [Older pricing](https://know.rendernetwork.com/basics/how-much-does-rndr-cost), [current pricing](https://rendernetwork.com/pricing)
- **[INFERENCE]** Frame approval provides a concrete task-acceptance model; it is not a universal correctness proof for AI results. Rendering API access and rendering-node onboarding are already gated, and the AI waitlist must not be promoted to evidence of universally available general GPU rental.
- **Gap:** No frame job, API whitelist access, emission transaction, withdrawal or AI-subnet booking was tested. We did not reconcile the AI-subnet storage contradiction through an actual admission process.

## 3. What should Global Exchange borrow without violating its constraints?

### Takeaway
**[INFERENCE]** With the approved static GitHub Pages/Git-record architecture, the credible near-term role is discoverable, machine-readable provider/task records and explicit handoff into independently operated execution/payment systems—not an implied escrow, wallet, verification service or always-on scheduler.

### Cited Findings
- Offer and lifecycle models differ materially: Akash deployment bids/leases, Golem negotiated resource coefficients, Vast host-set component prices, io.net mutable running-booking rates, and Render scene/frame jobs. A single ambiguous “price” field would erase differences visible in official documentation. [Akash](https://akash.network/docs/getting-started/core-concepts/), [Golem](https://docs.golem.network/docs/golem/payments), [Vast](https://docs.vast.ai/guides/reference/billing), [io.net](https://io.net/docs/guides/payment/pay-as-you-go), [Render](https://rendernetwork.com/pricing)
- Agent-capable interfaces are not equivalent permission models: Akash offers an agent skill with API/self-custody choices; Golem requires a funded local service; io.net and Vast expose account/API workflows; Render's local API is whitelisted. [Akash agents](https://akash.network/docs/getting-started/ai-agents/), [Golem GPU tutorial](https://docs.golem.network/docs/creators/javascript/tutorials/AI-on-golem-network), [io API](https://io.net/docs/guides/intelligence/io-intelligence-apis), [Vast pricing/API links](https://docs.vast.ai/guides/pricing), [Render API](https://know.rendernetwork.com/the-render-network-api)

### Inferences
- **[INFERENCE]** Useful Git-backed records should distinguish workload type, interface/access prerequisites, provider identity, source/retrieval date, quoted currency, pricing unit, minimum billed duration, storage/bandwidth, interruption conditions, funding mechanism, settlement destination and result-acceptance evidence. Static publication can expose those fields without holding money or secrets.
- **[INFERENCE]** “No platform running cost” is not “free compute.” Buyers still incur third-party compute fees and, where relevant, blockchain gas; providers still bear hardware/operations costs. Record these boundaries rather than promising a nonexistent Global Exchange checkout.
- **[INFERENCE]** Labels should distinguish provider-declared, platform-tested, reviewer-attested and transaction-observed evidence. A Git record or platform badge alone is not proof that the task ran correctly or that funds reached the recipient.
- **[INFERENCE]** Handoff links and user-controlled local agents can fit static discovery. Server-side secret storage, continuous price synchronization, payment custody, automated refunds and guaranteed dispute resolution would require capabilities beyond the approved design unless separately supplied and explicitly disclosed.

### Gaps
- This research does not select a payment processor, blockchain, wallet, custody model or dispute operator for Global Exchange. None is assumed to exist.
- A real end-to-end integration would need separately authorized runtime/payment testing, current terms and regional eligibility review. The present evidence supports comparison and interface design, not claims of audited or production-safe interoperability.
