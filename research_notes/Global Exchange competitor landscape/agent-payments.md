# Agent-payment infrastructure: five existing projects

## Which projects exist, and what do they actually provide?

### Takeaway

Exactly five projects are covered: Coinbase x402, Google AP2, Nevermined, Skyfire, and Payman AI. None is established here as a raw-compute exchange; x402 and AP2 are adjacent protocols, Nevermined and Skyfire combine payment infrastructure with service-discovery/monetization overlap, and Payman now emphasizes governed banking agents. These classifications are analytical, based on the official product and specification sources below.

Research retrieval date for **every linked source: 2026-11-18**. Sources were read without signing in, funding accounts, installing SDKs, or sending transactions. “Documented” means an official specification/product/API claim, not independently demonstrated settlement. No candidate was substituted: Payman's live homepage and current official integration repository establish credible existence even though its older documentation hostname could not be fetched.

### Inferences

- The direct competitive threat is **discovery plus payment orchestration**, especially Nevermined Catalog, not merely a payment protocol. x402 and AP2 are complementary layers rather than substitutes: x402 describes payment exchange, while AP2 describes authorization and transaction evidence. [x402](https://docs.x402.org/introduction), [AP2](https://ap2-protocol.org/ap2/specification/), [Nevermined Catalog](https://nevermined.ai/docs/products/catalog/overview.md)
- A “zero platform running cost” directory is compatible with listing providers that charge their own payment/service fees; it is not equivalent to free payment execution. Hosted rail costs and responsibilities must remain explicit and external. [CDP pricing](https://docs.cdp.coinbase.com/x402/seller/facilitator), [Nevermined Router fees](https://nevermined.ai/docs/products/catalog/router/how-it-works.md)

### Gaps

- No independent task execution, payment transaction, withdrawal, refund, production uptime measurement or security audit was performed. The comparison deliberately distinguishes official implementation evidence from operational proof.
- Current geographic eligibility, contract terms, dispute coverage and complete fee schedules were not established for every commercial platform. These are onboarding questions, not properties inferable from API documentation.

## What does the project-specific evidence establish, and where does it stop?

### Takeaway

Use current specifications and integration contracts, not launch-era descriptions. Two particularly important freshness corrections are AP2's v0.2 mandate terminology and Payman's current banking/Genie positioning; Nevermined's card-plan and Catalog purchase paths must also not be conflated. [AP2 specification](https://ap2-protocol.org/ap2/specification/), [Payman](https://paymanai.com/), [Nevermined payment types](https://nevermined.ai/docs/products/payments/overview.md)

### Cited Findings

#### 1. Coinbase x402

- **Existence and scope:** Official protocol docs describe an Apache-2.0 open standard around HTTP 402, designed for human developers and machine clients buying APIs/content. Docs link the x402 Foundation repository; “Coinbase x402” should not imply a mandatory Coinbase-only network. [Introduction](https://docs.x402.org/introduction)
- **Actual workflow:** The resource server returns payment requirements, the buyer selects a scheme/network and submits a signed payload, and the server verifies and settles itself or through `/verify` and `/settle`. Current headers include `PAYMENT-REQUIRED`, `PAYMENT-SIGNATURE` and `PAYMENT-RESPONSE`. [Facilitator](https://docs.x402.org/core-concepts/facilitator.md)
- **Production offering versus protocol:** Coinbase's hosted CDP facilitator requires API credentials, performs KYT/OFAC screening and lists production networks. Published pricing is first 1,000 onchain facilitator transactions/month free, then $0.001 per transaction; verification is free. These are **retrieved provider terms**, not a guarantee of free infrastructure forever. Its Bazaar extension indexes advertised endpoints after settlement, so there is real architectural discovery overlap. [CDP facilitator](https://docs.cdp.coinbase.com/x402/seller/facilitator)
- **Custody and failure handling:** The facilitator is documented as not holding funds. Settlement can remain pending or time out with an indeterminate result; production implementations require reconciliation, and direct Solana settlement needs duplicate protection. These are meaningful implementation obligations, not features a static directory automatically acquires. [Facilitator](https://docs.x402.org/core-concepts/facilitator.md)
- **Maturity:** Technical docs, multiple facilitator options and an explicit hosted production service go beyond a press announcement. Coinbase also reports historical processing totals, but no independent chain reconciliation was done here and those figures are not used as market metrics. [Production options](https://docs.x402.org/dev-tools/facilitators.md), [CDP](https://docs.cdp.coinbase.com/x402/seller/facilitator)
- **Boundary:** The protocol's described verification concerns the payment payload and settlement, not benchmark accuracy, model quality, GPU existence, task completion or SLA fulfillment. Treat compute verification as a separate requirement. [Facilitator responsibilities](https://docs.x402.org/core-concepts/facilitator.md)

#### 2. Google Agent Payments Protocol (AP2)

- **Current artifact:** Retrieved specification is explicitly **v0.2**. The official index links public SDK/source and human-present cards, human-not-present cards, x402, and Android credential samples; it states standardization will continue in FIDO working groups. [Specification](https://ap2-protocol.org/ap2/specification/), [Official index](https://ap2-protocol.org/)
- **Actual product:** This is a protocol/security feature within a commerce protocol, not a hosted wallet, payment processor or marketplace. Catalog APIs, checkout updates and role-to-role commerce APIs are explicitly outside AP2's scope. [Specification](https://ap2-protocol.org/ap2/specification/)
- **Human and autonomous modes:** Direct mode obtains user signatures for a particular checkout/payment. Autonomous mode obtains open mandates containing constraints and an agent public key; the agent later signs closed mandates within those constraints. Current primary mandate types are **Checkout Mandate** and **Payment Mandate**, each with receipts; do not summarize v0.2 only using older “Intent/Cart Mandate” terminology. [Specification](https://ap2-protocol.org/ap2/specification/)
- **Trust/settlement:** The Trusted Surface must be non-agentic; all role verification must happen in deterministic code. Credential provider, merchant and merchant processor have distinct obligations, and ordinary external payment credentials/rails carry the actual transaction. Cryptographic evidence does not remove those parties. [Specification](https://ap2-protocol.org/ap2/specification/)
- **Explicit limitations:** Agent-to-agent mandate delegation is outside current scope. Dispute evidence is defined, but dispute-resolution procedures, retention and retrieval requirements are not. The homepage separates initial card support from roadmap payment types; samples must not be equated with every rail being deployed. [Specification](https://ap2-protocol.org/ap2/specification/), [Index](https://ap2-protocol.org/)

#### 3. Nevermined

- **Seller monetization:** Registers HTTP endpoints, creates plans and checks entitlement before service execution. Docs cover prepaid and pay-as-you-go plans, metering, per-call pricing and seller payouts. Stablecoin payouts go to wallets; fiat payouts require the relevant seller payment-provider setup, including Stripe Connect in the overview. [Overview](https://nevermined.ai/docs/getting-started/overview)
- **Three distinct products/workflows:** Catalog purchases external HTTP-402 services per request; Embedded Web Flow lets a person confirm a card checkout; Merchant Plans let agents buy credits, time or pay-as-you-go access with cards or stablecoin. Card delegation for a plan is not a universal payment method for every Catalog listing. [Payments](https://nevermined.ai/docs/products/payments/overview.md)
- **Discovery overlap:** Catalog is a human-browsable and agent-readable directory of external AI services with a public unauthenticated feed. The Router pays services using a shared budget; it excludes ordinary monthly-billed, long-lived-API-key services lacking on-wire per-call prices. That is a narrower but tangible alternative to open task/provider discovery. [Catalog](https://nevermined.ai/docs/products/catalog/overview.md)
- **Authorization/custody:** Card enrollment is browser-tokenized; delegation sets caps, expiry and transaction constraints, with passkey binding documented for Visa. For the crypto Router, docs state funds stay in the buyer's wallet while Router-signed credentials authorize a merchant pull. This is a vendor-described noncustodial funds model, not a finding that users can ignore signing authority or service dependency. [Payments](https://nevermined.ai/docs/products/payments/overview.md), [Router](https://nevermined.ai/docs/products/catalog/router/how-it-works.md)
- **Pricing and consequences:** Router documentation currently states a 2% routing fee added to merchant payment, with actual per-payment fee fields authoritative. A delegated cap is authorization, not funding; an underfunded x402 wallet can leave budget reserved until reconciliation. Service failure does not automatically prove payment failed or entitle the buyer to a refund. [Router custody/fees](https://nevermined.ai/docs/products/catalog/router/how-it-works.md)
- **Maturity and source caveat:** Detailed live/sandbox environments and integration examples are present; Catalog docs explicitly warn listings settle real value on mainnet and sandbox has only limited rehearsal merchants. Some same-page generalized language says the Router checks wallet funds, while the detailed custody section says **no x402 balance precheck**; prefer the rail-specific caveat and do not claim blanket prefunding validation. No transaction was attempted. [Catalog](https://nevermined.ai/docs/products/catalog/overview.md), [Router](https://nevermined.ai/docs/products/catalog/router/how-it-works.md)

#### 4. Skyfire

- **Current structure:** Official platform page, updated **2026-11-03**, describes users, role-specific agents, API keys, agent wallets managed by Skyfire, and seller services. Buyer agents purchase; seller agents publish services, verify token signatures/claims and charge them. [Platform structure](https://docs.skyfire.xyz/docs/platform-structure)
- **Token semantics:** `kya` proves identity only; `pay` authorizes payment; `kya-pay` combines them. Delivery precedes charging in the documented standard sequence. Identity tokens are not themselves a payment receipt. [Introduction](https://docs.skyfire.xyz/docs/introduction-to-skyfire)
- **Settlement constraints:** Token issuance commits its amount against wallet balance. Sellers can charge actual amounts up to the remaining committed balance. Tokens last 10 seconds to 24 hours; a token validated before expiry can be charged during a further 24-hour grace period. Full settlement follows within a documented three-hour window, potentially about 51 hours total; above $1 cumulative charges the three-hour settlement window begins sooner. These are vendor-stated lifecycle rules, not measured latency. [Payments & Settlement, updated 2026-07-13](https://docs.skyfire.xyz/docs/payments-settlement)
- **Trust:** Skyfire guarantees payment up to a valid token's committed amount according to its docs; this is dependence on Skyfire's enforcement and wallet infrastructure, not a trustless escrow claim. Account deactivation does not void already-issued chargeable tokens. [Settlement](https://docs.skyfire.xyz/docs/payments-settlement)
- **Broader commerce:** October 2026 card documentation explains buy-now/buy-later authorization, merchant/amount limits and identity tokens presented during search, cart and checkout. Acceptance remains merchant-specific; introductory “everywhere” language should not be taken as demonstrated universal website access. [Card commerce, updated 2026-10-01](https://docs.skyfire.xyz/docs/agentic-commerce-with-payment-cards)
- **Maturity boundary:** Published dashboard/API workflows and dated implementation docs are stronger than projections, but neither successful onboarding, actual wallet withdrawal nor independently verified settlement guarantees were established in this research. [Platform](https://docs.skyfire.xyz/docs/platform-structure), [Settlement](https://docs.skyfire.xyz/docs/payments-settlement)

#### 5. Payman AI

- **Current existence:** Live homepage currently targets banks and credit unions with conversational payments, transfers and account analysis under institutional policies. This is materially different from treating Payman solely as an open agent-to-human bounty/payment API. [Current homepage](https://paymanai.com/)
- **Current developer artifact:** Official `PaymanAI/genie-mcp-stdio` repository describes a local bridge to the remote Genie payments-agent MCP server and provides source, configuration and OAuth integration details. `ask_genie` accepts a natural-language request; users sign in through a browser and connect a finance provider in Genie's UI. Fuller agent access requires human approval. [Official repository](https://github.com/PaymanAI/genie-mcp-stdio)
- **Settlement/custody claims:** Payman says it uses existing banking rails and that the regulated institution—not Payman—holds funds, licensing and KYC. The retrieved current sources do not establish all supported finance providers, currencies, external payout destinations or settlement time guarantees. [Homepage](https://paymanai.com/), [Genie repository](https://github.com/PaymanAI/genie-mcp-stdio)
- **Controls and limitations:** Payman describes separate deterministic policy enforcement, authenticated actions, audit trails and bank-held kill switch. Its own safety material says no system is guaranteed immune to prompt injection. The homepage claims SOC 2 Type II, but the underlying report was not examined: **do not label the system audited or production-safe on this research alone**. [Homepage](https://paymanai.com/), [Safety material, updated 2026-10-09](https://paymanai.com/resources/ai-banking-safety)
- **Integration constraint:** Genie remote MCP does not support dynamic OAuth client registration; direct hosts must be preregistered, while its published bridge uses a preregistered native client. The public bridge demonstrates integration availability, not banking access for every user. [Repository](https://github.com/PaymanAI/genie-mcp-stdio)
- **Legacy documentation discrepancy:** Search still surfaced official legacy documentation for generic agent-wallet send-payment APIs, but direct fetches of `docs.paymanai.com/overview/introduction` and `/capabilities/send-payment` failed with `getaddrinfo ENOTFOUND`. Treat those indexed descriptions as **historical/unverified current availability**, not evidence of an active public payment API. The current live homepage and repository are sufficient to retain Payman in the five-project set; no substitution is needed. [Legacy overview, fetch failed](https://docs.paymanai.com/overview/introduction), [Legacy send-payment, fetch failed](https://docs.paymanai.com/capabilities/send-payment), [Current homepage](https://paymanai.com/), [Current source](https://github.com/PaymanAI/genie-mcp-stdio)

### Inferences

- **Verification must be layered:** signatures establish authorization or payment evidence; they do not establish that a purchased computation met a task's acceptance criteria. None of the examined payment contracts should substitute for provider capability checks, execution receipts and task-specific evaluation. This follows from their documented responsibilities, not from a claim that the broader ecosystems lack all verification products. [x402](https://docs.x402.org/core-concepts/facilitator.md), [AP2](https://ap2-protocol.org/ap2/specification/), [Skyfire](https://docs.skyfire.xyz/docs/payments-settlement)
- **Different trust models must remain visible:** an x402 noncustodial facilitator, Nevermined delegated signing, Skyfire-managed wallets and Payman institution-held funds are not interchangeable meanings of “agent wallet.” [x402](https://docs.x402.org/core-concepts/facilitator.md), [Nevermined](https://nevermined.ai/docs/products/catalog/router/how-it-works.md), [Skyfire](https://docs.skyfire.xyz/docs/platform-structure), [Payman](https://paymanai.com/)

### Gaps

- Payman's old documentation availability could not be resolved beyond the reported DNS failure and newer official sources; do not infer either total product shutdown or continued legacy API operation.
- No audit report, contract enforcement review, authenticated account test or comparative task-quality benchmark was collected. These notes support landscape categorization and integration priorities, not procurement certification.

## Should Global Exchange integrate these projects or compete with them?

### Takeaway

**Recommendation:** preserve the approved static GitHub Pages/Git-record architecture. Integrate at the level of discoverable capabilities and external handoff first; do not imply Global Exchange already has a wallet, processor, settlement backend or custody model. This is a design recommendation under the supplied project constraints, not a statement that code has been implemented.

### Cited Findings

- x402's paying client and merchant resource server are operational roles; managed Coinbase facilitation requires server-side credentials and can incur usage fees. A static catalog can link to such endpoints without operating those roles itself. [x402 facilitator](https://docs.x402.org/core-concepts/facilitator.md), [CDP](https://docs.cdp.coinbase.com/x402/seller/facilitator)
- AP2 explicitly leaves catalog/commerce APIs outside its scope; adopting its evidence concepts does not provide a marketplace or payment processor. [Specification](https://ap2-protocol.org/ap2/specification/)
- Nevermined already combines service discovery, routing and spending budgets; Skyfire already combines service publication, identity and wallet settlement. A new exchange would compete directly if it rebuilds those hosted functions, not merely by indexing providers. [Nevermined Catalog](https://nevermined.ai/docs/products/catalog/overview.md), [Skyfire platform](https://docs.skyfire.xyz/docs/platform-structure)
- Payman's present workflow depends on financial institutions or connected finance providers, making it a less immediate fit for permissionless per-call compute procurement. [Homepage](https://paymanai.com/), [Genie repository](https://github.com/PaymanAI/genie-mcp-stdio)

### Inferences

- **x402: integrate, high relevance.** Allow provider records to declare an external paid endpoint, protocol/version, network/asset, pricing reference and provider-owned documentation. Buyers bring their own compatible client/wallet. Do not place facilitator secrets in public Git records or browser-delivered configuration; do not promise automatic payment from merely listing an endpoint. Basis: [x402 flow](https://docs.x402.org/core-concepts/facilitator.md), [CDP credentials](https://docs.cdp.coinbase.com/x402/seller/facilitator).
- **AP2: track and selectively align, not compete.** Keep task scope, budget, expiry, approval and receipt references conceptually compatible; defer claims of AP2 compliance until an actual signing/verifying flow exists. Public Git should not be a raw store for sensitive payment mandates or credentials. Basis: [AP2 roles/privacy and mandate requirements](https://ap2-protocol.org/ap2/specification/).
- **Nevermined: integrate and differentiate.** Link eligible providers to their Nevermined purchase route and label the account/funding dependencies. Compete on transparent provider evidence, portable Git records, heterogeneous compute/task offerings and discovery across rails—not on recreating a hosted router or billing engine. Basis: [Catalog scope](https://nevermined.ai/docs/products/catalog/overview.md), [Router obligations](https://nevermined.ai/docs/products/catalog/router/how-it-works.md).
- **Skyfire: optional integration.** Expose that a provider accepts Skyfire and whether verified identity/payment tokens are required; leave managed accounts, token issuance and settlement with the external service. Do not make Skyfire identity compulsory for every exchange participant. Basis: [Platform structure](https://docs.skyfire.xyz/docs/platform-structure), [Identity/payment separation](https://docs.skyfire.xyz/docs/introduction-to-skyfire).
- **Payman: monitor and link where applicable.** Suitable for institution-backed agent payment execution or a buyer already using Genie, not an assumed default payout API. Reassess current provider availability and onboarding before any implementation decision. Basis: [Current positioning](https://paymanai.com/), [MCP registration and provider connection](https://github.com/PaymanAI/genie-mcp-stdio).
- **Shared record principle:** payment status and task outcome should be separate assertions, each with provenance and clear verification level. A provider's declared payment acceptance is not a verified completed transaction, and a settlement reference is not a successful computation. Basis: the distinct payment/commerce responsibilities in [AP2](https://ap2-protocol.org/ap2/specification/) and [x402](https://docs.x402.org/core-concepts/facilitator.md).

### Gaps

- Selecting a payment operator, implementing buyer signing, retaining private receipts, processing refunds or guaranteeing job outcomes would be new product/operational decisions beyond the approved static architecture. Nothing in this research authorizes or implements those changes.
- No claim is made that external integrations are available without eligibility checks, fees, account setup or future maintenance. Provider terms and capabilities require rechecking when implementation is actually proposed.
